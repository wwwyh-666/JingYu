## 2. 三层数据结构

### 2.1 Source（来源）

`data/sources.json`，一条来源 = 一个可追溯的官方页面：

| 字段 | 说明 |
|---|---|
| `source_id` | 如 `SRC_ZYM_WWJ_001` |
| `title` / `institution` / `url` | 页面标题、机构、URL |
| `accessed_on` / `published_on` | 访问日期 / 页面发布日（可空） |
| `locator` | 页面内定位方式（栏目、段落、检索词） |
| `review_status` / `reviewer` / `reviewed_at` | 来源级人工审核 |
| `approved_evidence_ids` | **来源级白名单**：本来源允许用于回答的证据 ID 清单 |

来源批准 ≠ 整页放行。例如 `SRC_ZYM_WWJ_001` 只白名单化 4 条证据；`SRC_TT_OFFICIAL_QND_001` 只白名单化 2 条。

### 2.2 Fact（事实卡）

`data/facts_{SPOT}.json`，一条事实 = 一个可以单独提问、单独核验的陈述：

| 字段 | 说明 |
|---|---|
| `fact_id` / `spot_id` / `object_id` / `period` | 事实身份与时空范围（period 是字符串，不是年代解析） |
| `text` | 审核人确认的最终表述（不是网页原句照搬，可收窄） |
| `source_ids` / `source_locator` | 该事实声明的全部来源及定位 |
| `keywords` / `query_aliases` | **检索元数据**（人工登记，用于关键词匹配） |
| `review_status` / `reviewer` / `reviewed_at` | 事实级人工审核 |
| `dispute_status` | `disputed` 时整条事实不可发布 |
| `statement_type` | `direct_source_paraphrase` / `multi_source_synthesis` |
| `source_evidence[]` | 逐来源声明 `supports/context_only/conflicts` 与定位说明 |

### 2.3 Evidence（原文证据）

`data/evidence_{SPOT}.json`，一条证据 = 一段**可机检的原文**：

| 字段 | 说明 |
|---|---|
| `evidence_id` / `fact_id` / `spot_id` / `object_id` / `period` | 与事实严格对齐，不一致即不可发布 |
| `source_id` / `url` | 所属来源，URL 必须与来源登记完全一致 |
| `quote` | 原文片段（不改字、不拼接不连续句） |
| `locator` | 页面内精确定位 |
| `quote_sha256` | `sha256(quote)`，加载时自动复算 |
| `usage` | `answer`（可直接支撑回答）/ `context_only`（仅背景，不能单独支撑）/ `suspected_typo`（疑似错字，永不提供） |
| `review_status` / `reviewer` / `reviewed_at` | 证据级人工审核 |

### 2.4 三层关系

```text
Fact ──source_ids──► Source ──approved_evidence_ids──► Evidence
 │                                                        │
 └──source_evidence[]（逐来源定位与 relation）◄────────────┘ fact_id/spot/object/period 对齐
```

一条证据要能进入回答，必须同时满足（`Repository.evidence_is_publishable`）：

1. 事实 approved、有审核人与日期、未被标记 disputed；
2. 事实声明的**每个**来源都 approved；
3. 证据 approved、有审核人与日期；
4. 证据的 `source_id` 在事实来源内，URL 与来源一致；
5. 证据 ID 在来源的 `approved_evidence_ids` 白名单内；
6. `fact_id/spot_id/object_id/period` 与事实完全一致；
7. `usage != suspected_typo`；且该事实至少有一条 `usage=answer` 证据。

## 3. SHA-256 完整性校验

- 每条 Evidence 的 `quote_sha256` 在**每次加载**时由 Pydantic 校验器复算比对，不一致 → 整个知识库拒绝加载（接口返回 `KNOWLEDGE_DATA_INVALID`）。
- 测试 `test_tiantan_release_scope.py` 与 `test_eight_spots_retrieval.py` 对全部 25 条 quote 复算哈希。
- 作用：防止 quote 被误改、被截断或被替换后仍按"已审原文"发布；**不代表内容本身必然正确**。

## 4. 人工审核流程

```text
候选：官方来源检索 → 记录 URL/机构/访问日期/locator
   → 事实卡候选（优先 direct_source_paraphrase）
   → 原文 Evidence（quote 原样 + 定位 + 哈希）
   → 候选包留档 docs/candidate/{主题}_{日期}/
   → 人工审核（确认文字、收窄夸张表述、决定 period/关键词）
   → 写入正式 data/（事实/证据/来源白名单）+ reviews_{fact_id}.json 独立审核记录
   → 离线回归（哈希、门禁、隔离、检索）→ 才可用于回答
```

规则：

- 审核人必须给出**明确文字确认**；文档中的"批准"以 `data/` 与 `reviews_*.json` 为准。
- 原文用字与最终表述不一致时（如"由胜至衰"→"由盛转衰"、省略"灰筒瓦绿琉璃剪边"），必须在审核记录中说明为同义转写或收窄，不得静默改写。
- 不连续的两句原文不得拼成一条 quote；必须拆成两条证据（天坛 003/004、正阳门 001/002 均如此）。

## 5. 状态含义

| 状态 | 含义 | 是否可用于回答 |
|---|---|---|
| `pending_human_review` | 已整理、待人工审核 | 否 |
| `approved` | 审核人签字确认（必须带 reviewer/reviewed_at） | 是（还需其余门禁全通过） |
| `rejected` | 审核不通过 | 否 |
| `disabled` | 主动停用 | 否 |
| `dispute_status=disputed` | 存在未决年代/记载冲突 | 否（整条事实阻断） |
| `usage=answer` | 可直接支撑 claims | 是 |
| `usage=context_only` | 仅作背景，不能单独支撑 | 否（不能单独用） |
| `usage=suspected_typo` | 疑似错字，不作为结论、也不提供给生成模型 | 否 |

## 6. 为什么不是"把网页交给大模型"

如果直接把网页丢给模型：

- 网页可能包含未审内容、广告、路线推荐、与服务无关的段落；
- 模型会用自己的记忆补充历史细节，产生"看起来对但无出处"的句子；
- 事后再让模型自查，本质是"自证"，无法定位到具体证据；
- 出错时无法回答"依据哪一句、哪一页、谁审的"。

本系统的约束链是：

1. **只有人工审核过的事实与原文**能进入模型上下文（关键词检索、景点隔离、可发布性门禁）；
2. 模型只能输出结构化 claims，每条必须挂 `fact_id + evidence_ids`；
3. **程序**逐条核对 fact/evidence 的范围、白名单、用途（不依赖模型自觉）；
4. **另一个独立模型请求**只拿证据和候选做对照，不给生成过程；
5. 核验必须全部 `supports` 才发布，否则修订一次或直接拒答；
6. 发布时返回 `citations` 与 `evidence`（含 quote、locator、URL、哈希），前端可展示"本次依据"。

因此系统可以回答"这句是谁说的、原文是什么、审核人是谁、模型是否被核验过"，也敢于在资料不足时拒答。
